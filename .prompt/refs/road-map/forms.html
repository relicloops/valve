02 · grammar and vocabulary

Name every attachment.

Valve models assignment style globally and option spelling per schema entry. The existing grammar is deterministic. Each missing form adds a different ambiguity surface, so cost is ranked against the parser as it exists today.

design equation 
assignment style
  × option type
  × value kind
  = accepted token

orthogonal concerns · no redundant form bits

POSIX core

The vocabulary Valve builds on.

POSIX names options, option-arguments, and operands. Long options, enable/disable toggles, and targeted help are extensions layered on that base.

option
A named flag that changes utility behavior, such as -f or --force.
option-argument
The value associated with an option, such as fast in --lane=fast.
operand
A positional argument whose meaning comes from its location rather than a flag name.
end-of-options marker
The special token --; everything after it must be treated as operand data.
inline / attached
The value shares one argv element with its option, normally separated by =.
separate / detached
The value occupies the next argv element after its option name.

Operands

Position supplies the meaning.

Options are named; operands are positional. A parser should preserve operand insertion order and leave the consumer responsible for mapping each index to application behavior.

standard utility 
cp  -r  src/  dest/
│   │   │     └─ operand[1]
│   │   └─────── operand[0]
│   └─────────── option
└─────────────── utility
future Valve boundary 
operand[0] = "filename.log"
operand[1] = "7890"

consumer:
  0 → --log-path
  1 → --listening-port
today

Valve rejects ordinary positional tokens. The declared VL_BEHAVIOR_ACCEPT_OPERANDS flag is not wired, its documented public accessors do not exist, and -- currently discards the remaining tail instead of collecting it.

Syntax matrix

What the parser accepts today.

Inline and separate forms are both implemented, but the executable selects exactly one assignment mode. Bare booleans remain valid in either mode.

Form Example Status Current behavior or missing rule
Long inline --flag=value complete Accepted in VL_ASSIGN_INLINE.
Long separate --flag value complete Accepted in VL_ASSIGN_SEPARATE.
Short inline -f=value complete Accepted in VL_ASSIGN_INLINE.
Short separate -f value complete Accepted in VL_ASSIGN_SEPARATE.
Both attachment modes --flag=value and --flag value missing Add an assignment policy accepting both existing branches.
Long joined --flagvalue missing Define name-prefix matching and ambiguity precedence.
Short joined -fvalue missing Split after the short name and coordinate with clusters.
Short stacking -abc missing Expand members and reserve a value-taking final member.
Enable / disable --enable-X extension Complete: both prefixes map to one toggle option.
Dotted name --proxy.lane=fast extension Complete: exact match, typed target, grouped and targeted help.
Operand file.txt missing Behavior bit is declared; storage, accessors, lifecycle, and parsing are absent.

Implementation expense

Operands are the largest missing parser surface.

This is relative engineering cost, not delivery priority. Percent rails communicate ordering only; they are not estimates of elapsed time.

1 · Operands + -- very high
2 · Short stacking high
3 · Long joined high
4 · Short joined medium
5 · Both assignment modes low
why operands rank first

They add a new result family.

  • Public vl_operand_count() and vl_operand_at()
  • Owned storage, clearing, repeated-parse behavior, and destruction
  • Trailing and post--- collection rules
  • Disambiguation from separate option values
  • Disabled-mode errors and generated help notation
strict attachment answer

Long joined is the costliest attachment form.

Operands and clusters are not option-argument attachments. Among the missing attachment forms, --flagvalue is most expensive because arbitrary long names create prefix ambiguity.

Ambiguity

Joined long values need a policy before code.

A parser cannot know where an arbitrary long name ends without consulting the schema. Multiple valid prefixes can still describe different parses.

API terminology

The simplified model is already in place.

Historical form-specific constants were replaced by one global assignment enum and combinable option-type bits. KV behavior is routed by value kind.
